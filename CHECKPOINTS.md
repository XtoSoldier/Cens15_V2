# Emergency Full Application Checkpoints

These endpoints are independent of the ordinary section-transfer endpoints. They create dated full application restore points, not arbitrary point-in-time recovery (PITR), database dumps, schema rollbacks or configuration backups.

## Scope

Every entity discovered through `AppDbContext.Model.GetEntityTypes()` is captured, including entities reached only by navigation properties, legacy permissions/role-permission links, responsibilities, users, authentication password hashes, login history, certificate templates, schedules, students and soft-deleted students, birth/contact/document records, enrolments, subjects, teaching assignments and grades. Every EF scalar property, primary key and foreign key is serialized using its actual CLR type. Query filters are disabled. Navigation graphs are not serialized.

All actual files below `wwwroot/uploads` are included as bytes, not just document references. Empty directories and filesystem attributes are not preserved. Nothing elsewhere in `wwwroot` is captured. Code, compiled binaries, `appsettings`, connection strings, email configuration, the JWT signing key, the checkpoint server key, the session epoch and the checkpoint registry are excluded. Back up application configuration and keys separately using an appropriate secrets-management procedure. A full checkpoint contains sensitive personal information and bcrypt credentials; it must remain encrypted.

Historical `Token` and `PasswordResetCode` scalar rows are captured for completeness, but both tables are cleared on restore rather than reactivating old codes or sessions. The externally persisted session epoch is rotated after a committed restore. Tokens without the new `session_epoch` claim are invalid, so deploying this change requires all existing sessions to log in again. The current administrator is not silently retained: log in with the restored snapshot's credentials. A snapshot must include an active `Admin` with a nonempty email and a parseable bcrypt hash (supported work factors 4 through 16).

## API Contract

All routes are under `/api/checkpoints` and require the `Admin` JWT role. Inside the exclusive gate, the service also checks the current epoch and confirms the user is still active and has role `Admin` and an Auth row in the current database. JSON responses use the application's Spanish camelCase convention.

| Method and Path | Body | Response |
| --- | --- | --- |
| `GET /api/checkpoints` | none | Array of checkpoint metadata |
| `POST /api/checkpoints` | `{ "nombre": "Before changes", "descripcion": "Optional" }` | Metadata |
| `POST /api/checkpoints/importar` | Multipart `archivo` (`.censbackup`), `clave` | Registered checkpoint metadata; **never restores data** |
| `POST /api/checkpoints/{id}/exportar` | `{ "clave": "at least 12 characters" }` | Binary attachment `checkpoint-{id}.censbackup` |
| `POST /api/checkpoints/{id}/preview` | none | Comparison, warnings, errors and opaque `huella` |
| `POST /api/checkpoints/{id}/restaurar` | `{ "huella": "from preview", "confirmacion": "RESTAURAR TODO", "crearRespaldo": true, "aceptarSinRespaldo": false }` | Restore result |

Metadata: `id`, `nombre`, `descripcion`, `creadoEn` (ISO UTC), `creadoPor` (user GUID), `automatico`, `tablas: [{ entidad, cantidad }]`, `cantidadArchivos`, `tamanoBytes` (encrypted server file size), `huellaEsquema`.

Registry metadata counts include the captured historical token/reset-code rows; preview `snapshot` counts for those two tables are zero because they are never reactivated during restoration.

Preview: `checkpointId`, `nombre`, `creadoEn`, `puedeRestaurar`, `tablas: [{ entidad, actual, snapshot }]`, `archivosActuales`, `archivosSnapshot`, `advertencias`, `errores`, `huella`. Entity labels are EF entity names (qualified names), not the four transfer-section names. `huella` is a random opaque capability, not a data/credential digest exposed to the client. It binds the caller, epoch, checkpoint ID and complete content, current database scalar data and migrations/schema, complete uploads contents and filenames, and a five-minute expiry. It is one-use; a failed restore attempt requires a fresh preview. Restart also invalidates previews. Any intervening change requires a new preview, including login-activity writes. The final check is performed while the current mapped tables are locked.

Restore result: `{ "restaurado": true, "respaldoPrevioId": "GUID or null", "requiereReingreso": true, "mensaje": "..." }`.

`crearRespaldo` defaults to `true`. A failure to save the automatic dated pre-restore point aborts the restore. To opt out, both `crearRespaldo: false` and `aceptarSinRespaldo: true` are required, as is exact confirmation `RESTAURAR TODO`. Saved dated points are never automatically deleted or overwritten and are outside the restored DB domain. Reimporting the same archive registers a new GUID without overwriting the original point; the imported creation date/name are retained, its registering administrator becomes `creadoPor` and `automatico` becomes false.

Validation errors are `400 { "message": "..." }`; authentication/authorization use 401/403, stale previews/incompatibility/storage conflicts use 409 with a readable message. Unknown GUIDs return 404. Unresolved recovery returns 503 and the instance does not serve ordinary requests. Invalid JSON/model binding under these routes returns a sanitized `400 { message }`. Host/proxy multipart limits can reject oversized requests with 413 before controller validation. Wrong passphrase or authentication-tag failure gives an explicit `Clave incorrecta o archivo cifrado alterado` error, without echoing secrets. Import additionally requires current model/schema/migration compatibility; an incompatible archive is rejected rather than registered as an unrestorable point.

Send passphrases only in POST bodies/form fields, never URLs or logs. The implementation does not log request bodies, decrypted content, hashes or cryptographic keys. Ensure reverse proxies, APM, HTTP tracing and EF sensitive-data logging do not record these bodies or database values. Use HTTPS and do not cache checkpoint responses.

## Encryption and Validation

The portable format is binary: 8-byte magic/version `CENSBK01`, 16-byte random salt, 12-byte random nonce, 16-byte authentication tag, then UTF-8 JSON ciphertext. AES-256-GCM authenticates both ciphertext and the first 36 header bytes. The portable key is PBKDF2-HMAC-SHA256 with 600,000 iterations and a random salt, derived from the user's 12-1024 character passphrase. Export uses a new salt and nonce every time. There is no ZIP extraction, decompression or unauthenticated archive payload.

Server files are encrypted with AES-256-GCM using a persistent random 32-byte `server.key` outside the web root. That key is never put into an archive. Portable encryption and at-rest encryption use different keys. Losing `server.key` makes existing server checkpoints unreadable; startup refuses to silently replace a missing key when saved points or recovery exist. A separately exported portable archive can still be imported using its passphrase and a newly provisioned server store.

The fixed upper bound is 128 MiB for the encrypted archive, with at most 96 MiB of raw uploads, 50,000 files and 1,000,000 total scalar rows. JSON/base64 overhead also counts against the bound, so actual capacity is lower. The implementation buffers snapshots in memory; provision several times the archive limit in available memory and sufficient disk for the saved point, optional pre-backup, staged uploads and old uploads. At most 1,000 pending preview bindings are retained per instance.

JSON is strict: unknown members, duplicate members (including case variants), excessive depth, missing/unknown EF entities or scalar fields, incompatible scalar types/nullability/lengths, duplicate keys/unique indexes, dangling foreign keys, unsafe paths, file/directory collisions and case-insensitive duplicate paths are rejected. Archives cannot supply executable SQL, CLR type names to instantiate, or restore commands. Relational writes are parameterized and table/column names come only from the local EF metadata. The local schema fingerprint covers EF scalar/table/relationship/index metadata, PostgreSQL column types/defaults/identity/nullability, constraints/index definitions and the currently applied migration history. Both fingerprint and history must match before restore; no migrations are run as part of restore. Future owned/shared/cyclic/keyless entity mappings or computed columns require explicit implementation rather than silent omission. Database constraints remain the final authority, and any constraint rejection rolls back.

Symlinks/reparse points in storage/upload paths or captured trees are rejected. Upload paths must be relative, use `/`, and contain no traversal, drive names, empty segments, Windows device names, trailing spaces/dots or invalid filename characters. Archives contain only regular file bytes, never symlink entries. Local OS administrators are outside this threat model; do not allow other principals to mutate checkpoint/recovery directories.

## Consistency and Recovery

A process-wide async reader/writer gate wraps ordinary requests **before static files and authentication**, including ordinary transfer endpoints. A capture/preview/restore takes the exclusive writer lease; checkpoint routes skip middleware acquisition to avoid self-deadlock and acquire the writer in the service. Ordinary requests and file reads cannot observe the intermediate state. Storage operations are serialized through the same gate. PostgreSQL transactions use serializable isolation and lock every mapped table `ACCESS EXCLUSIVE` in deterministic order, preventing concurrent SQL writes during capture/restore. Long-running requests or database writers may delay operations.

Restore stages validated file bytes under the private checkpoint store, outside `wwwroot`, before replacing any live files. It writes and flushes `restore.journal`, moves existing uploads to `{operation}.old` in the private store, and renames `{operation}.new` to the live uploads path. All mapped tables are truncated **together, without CASCADE**, followed by parameterized inserts preserving explicit scalar IDs in FK dependency order. Unknown external FK dependants therefore cause refusal, not deletion. Identity sequences are reset with transactional `ALTER SEQUENCE RESTART`, not nontransactional `setval`. A row in private PostgreSQL table `public."__CensCheckpointCommits"` is inserted in the **same transaction** as the replacement rows. This table is deliberately outside the EF snapshot domain.

On startup, before migrations, seeding or file providers, recovery reads that DB marker. A committed operation keeps the new uploads and rotates the external session epoch; an uncommitted operation restores the old uploads. The journal remains until a consistent outcome is established. Unreadable/malformed journals, unavailable databases or ambiguous/missing recovery files fail closed. Post-commit request cancellation does not interrupt the recovery decision. A response can fail after an ambiguous commit even when the transaction ultimately committed; re-login and inspect state rather than blindly repeating a restore. Keep both the journal and private files intact for operator investigation if recovery fails.

This is coordinated, journaled crash recovery, **not a distributed atomic transaction** between PostgreSQL and the filesystem. Files are written with write-through/flush before rename; durability still depends on filesystem/OS/storage rename and flush guarantees. Power-loss/filesystem corruption or manual deletion may require operator recovery and are not promised to be automatically repairable. Failed file swaps recover original uploads before ordinary traffic resumes. Private orphan staging/old directories from a crash during preparation/cleanup are not registry points and may require operator cleanup after recovery has completed. Never remove a journal or private operation files simply to make the application start.

## Deployment Requirements

Default storage is `<ContentRoot>/App_Data/checkpoints`. Override with `Snapshots:Directory` (environment variable `Snapshots__Directory`) as an absolute persistent private directory. It must neither be under nor contain `wwwroot`. Keep uploads and private storage on the **same filesystem/volume**, because directory rename is required. A cross-volume rename fails and the journal preserves a recoverable original state. Do not put private storage on ephemeral container storage, a publicly served directory, an externally published IIS virtual directory, or a network filesystem without suitable durability/rename/locking guarantees.

`App_Data/**` is excluded from project content/publish and `.gitignore`. If configuring a different path, exclude it from source control and publish independently. Unix private root is mode 0700 and atomic private files are 0600; on Windows configure an ACL allowing only the service identity and designated backup administrators. The service identity needs read/write/rename access to both upload and private directories. Secure the separate application configuration/secrets backup as well. TLS and host request-body limits must allow the desired archive size, and idle/request/database timeouts must be sufficient for maintenance operations.

Run **one application instance only** against this database/upload pair. The server-store lifetime lock rejects concurrent processes opening the same checkpoint directory, but cannot coordinate different directories pointing at one DB, external filesystem writers, scheduled jobs or another host. Stop those writers for maintenance. PostgreSQL table locks protect the mapped DB domain, not arbitrary external applications/files. Do not deploy an additional instance with a different private store against the same domain.

The database must already exist and the service identity must be able to create/query/insert the private marker table, lock/truncate/insert mapped tables and alter their identity sequences. Normal startup still runs the application's existing migrations and compatibility DDL after recovery; checkpoint restore itself never changes schema. Existing `DbSeeder.Seed` is skipped after the database contains any successful restore marker so that a restored authorization graph does not silently gain seed roles/responsibilities at the next restart. Version upgrades and intentional seeding/configuration changes remain a separate operator-controlled procedure. Do not delete marker rows or run the normal startup/seeder inside snapshot unit tests.

## Tests and Remaining Verification

`Tests/CheckpointTests.cs` uses only EF InMemory and isolated temporary directories. It covers all-model scalar discovery, soft-deleted contact/student rows, legacy relationships, actual files, encryption/tamper/wrong-passphrase guards, at-rest confidentiality, import-without-restore, current-store Admin/epoch checks, restore confirmation/backup opt-out, invalid schemas/fields/FKs/keys/paths/admin credentials, strict JSON, preview bindings, middleware/file gating and unsupported-provider restore refusal. It does not start `Program`, run migrations or connect to an actual database.

Run focused tests with `dotnet test Tests/CENS15_V2.Tests.csproj -c Release --filter FullyQualifiedName~CheckpointTests`. Release avoids the running Debug backend's locked binaries.

`Tests/CheckpointPostgresTests.cs` adds five explicitly opt-in local PostgreSQL integration tests. Set `CENS15_RUN_SNAPSHOT_POSTGRES_TESTS=true`; without that exact value these tests are skipped, while an opted-in configuration/connection/CREATEDB failure fails the tests rather than silently skipping. The fixture privately loads `appsettings.Development.json` through `ConfigurationBuilder`, refuses any host other than `localhost` or `127.0.0.1`, and has no connection fallback. It connects to maintenance database `postgres` solely to create/drop its own random `cens15_checkpoint_it_<32 hexadecimal GUID characters>` database. `EnsureCreated` and the checkpoint recovery marker initializer run only against that newly created database, never the application's configured database. No `Program`, migrations or application seeder is invoked. Each test disposes connections, drops only its validated generated database in cleanup and removes its own private directory under `C:\Users\ferma\AppData\Local\Temp\opencode\cens15_checkpoint_it_<GUID>`.

Run the integration suite in PowerShell from the backend directory:

```powershell
$env:CENS15_RUN_SNAPSHOT_POSTGRES_TESTS = 'true'
dotnet test Tests/CENS15_V2.Tests.csproj -c Release --no-restore --filter FullyQualifiedName~CheckpointPostgresTests
```

Verification completed on the local PostgreSQL 17 service: **5 integration tests passed, 0 failed, 0 skipped**. The combined Release run of `CheckpointPostgresTests` and `CheckpointTests` passed **23 tests, 0 failed, 0 skipped**. All generated databases and temporary directories were cleaned up successfully. No real application database, live API or running Debug process was accessed or modified.

The integration tests verify:

- Full encrypted export/import/restore with a nonempty row in every currently mapped EF entity, comparing every restored scalar/ID/FK except intentionally cleared historical token/reset rows. This includes legacy permissions, roles/responsibilities, users/auth hashes, schedules with `TimeOnly`, soft-deleted students with `DateOnly`, contact/birth/document data including `ImagenesUrl: List<string>`, academic relations/decimal grades, teaching assignments, templates, login history and all actual uploaded file bytes.
- Import-only registration leaves modified live DB rows and uploads unchanged; default pre-backup contains the immediately preceding DB/file state; successful restoration clears historical codes, rotates the persisted epoch, preserves the schema fingerprint and correctly restarts identity allocation for a subsequently inserted student.
- Separate stale-preview refusals for database changes and same-length file-content changes, without creating a backup or swapping files.
- An unmapped external FK causes PostgreSQL `TRUNCATE` refusal (`0A000`) without CASCADE; original DB rows, external rows, codes, uploads and epoch survive, while the saved pre-backup remains registered.
- A PostgreSQL CHECK constraint rejection (`23514`) after truncation/inserts restores original DB rows, files and epoch. Earlier transactional sequence restarts also roll back, demonstrated by inserting the next student without an identity collision after failure.
- Durable journal states after file swap with a rolled-back DB marker versus a committed DB marker. Fresh recovery/epoch objects restore old uploads for rollback or retain new uploads and rotate/persist the epoch for commit. Repeated initialization after resolved recovery does not rotate the epoch again.

The first PostgreSQL run exposed a production-path defect invisible to InMemory tests: the schema-fingerprint catalog query concatenated PostgreSQL's internal `"char"` identity field with text, producing SQLSTATE `42725`. `CheckpointModel.FingerprintAsync` now explicitly casts `attidentity` to text; all integration scenarios then passed. The full-roundtrip assertion compares properties by name rather than dictionary serialization order, because decoded sorted dictionaries can use a different string comparer from freshly captured ordinal dictionaries.

Remaining verification: these tests emulate durable journal/transaction boundary states; they do **not** kill a live process, interrupt power, corrupt storage, exercise every rename boundary, or prove filesystem durability under power loss. Dedicated backup-write-failure, rename-failure and host-level HTTP integration/fault-injection tests remain separate work. Any further destructive testing must continue to use newly provisioned disposable databases/private directories, never application data or the normal API. The documented single-instance and same-filesystem deployment requirements still apply.
